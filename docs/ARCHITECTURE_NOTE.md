# Architecture note

The running system is a FastAPI backend plus a small Next.js App Router frontend. On startup the backend validates the workbook relationships, stores the three data sheets in SQLite, parses the README snapshot timestamp, extracts all six PDFs in layout mode, splits them at numbered and known-issue headings, bounds long sections to roughly 450 words with overlap, tags each chunk with source status/account/authority metadata, and writes a cosine-distance Chroma collection (with an inspectable lexical sidecar fallback if the native Chroma runtime is unavailable). Chroma uses stable 384-dimensional feature-hashed word, word-pair, and character embeddings generated in-process. This avoids downloading or loading a large embedding model on memory-limited free-tier deployments. Search combines Chroma similarity with per-chunk lexical, exact-ID, topic, and account relevance. Source authority breaks close topical ties; it cannot promote unrelated boilerplate above a direct match.

The agent exposes five tool contracts: `search_documents`, `lookup_records`, `evaluate_entitlement`, `analyze_operations`, and `propose_escalation`. When configured, Groq receives the complete function set and is required to select a native tool; Gemini native function calling is the retry fallback. Ambiguous requests use this native selection. High-confidence action, access-sensitive, aggregate, cancellation, and credit intents have a deterministic safety path so provider latency or the daily routing cap cannot turn them into an unrelated lookup. For customer-named entitlement scenarios without an ID, the repository resolves the authorized account and best matching real order before the evaluator performs timestamp arithmetic and parses applicable agreement overrides. The evaluator, repository, analytics query, and action ledger remain server-side regardless of model output.

`lookup_records` supports both ID-based reads and scope-aware listings. A request for another agent's/customer's records is represented as `query_scope=other_accounts`, then explicitly denied by the repository for non-manager sessions. `analyze_operations` reads the real SQLite tickets table, groups materially similar ticket subjects, counts distinct affected accounts, and distinguishes cross-customer recurrence from repeated tickets belonging to one customer.

Every lookup resolves the record's account from SQLite and checks the signed mock session's scope before returning data. Document agreement filters are narrowed by that same scope. A supplied account ID can narrow a query but cannot widen access. Viewer sessions cannot propose actions. A proposal is stored as `pending_confirmation`; only the protected confirm endpoint, with `confirmed: true`, writes the action ledger, and repeat confirmation is idempotent.

Reliability is deterministic: active account agreement > current SOP/policy > current product guide; deprecated v2 is excluded; ticket history is context-only and unverified. Missing pickup facts produce `needs_verification`. The supplied dataset snapshot is used as the time basis. The main trade-offs are ephemeral Render storage, startup ingestion/cold starts, a local no-key planner for reproducible demos, and free-tier provider latency/rate limits.
